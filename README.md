# Task 1
# Кейс: Моделирование процесса выдачи ИТ-оборудования (BPMN 2.0)

Этот проект демонстрирует навык системного анализа: перевод неструктурированного текстового описания бизнес-процесса в формальную нотацию BPMN 2.0, а также выявление логических противоречий и "белых пятен".

## Исходное описание задачи (Входные данные)

**Контекст:** В компании «X» работает выдача ИТ-оборудования пользователям по заявке, которую надо оформлять в системе №1. 

**Рабочий поток:**
1. Пользователь офиса делает заявку через почту или по телефону в 1-ую линию технической поддержки. Он получает номер обращения для отслеживания статуса. 
2. Первая линия ТП делает заявку на оборудование (на основании заявки пользователя) в системе №2 отделу снабжения. 
3. Отдел снабжения принимает заявку в системе №2 (получает уведомление на почту и видит в личном кабинете). 
4. Снабжение проверяет наличие оборудования в системе №3. 
   * **Если оборудование есть:** снабжение вызывает логистику и отправляет оборудование первой линии ТП. ТП выдаёт оборудование пользователю и закрывает заявки в системах №1 и №2.
   * **Если оборудования нет:** снабжение делает заявку на закупку поставщику через почту и ждёт поставку. После привоза снабжение проводит приём в системе №3, вызывает логистику и передаёт оборудование ТП. ТП выдаёт оборудование и закрывает заявки в системах №1 и №2.
5. В конце процесса пользователь получает оборудование и может выставить оценку сервиса технической поддержке.

## Результат: BPMN-модель 

На основе текста спроектирована модель. Выделены пулы и дорожки (Пользователь, 1-я линия ТП, Отдел снабжения, Поставщик), а также визуализировано взаимодействие между ИТ-системами.


## Выявленные противоречия и "белые пятна" 
В ходе моделирования к исходному описанию были сформулированы вопросы, требующие уточнения у заказчика для построения корректной модели:

1. **Отказ поставщика:** Что происходит, если оборудования нет ни на складе, ни у поставщика? (Отсутствует альтернативный сценарий завершения).
2. **Бюджет и согласование:** Кто принимает решение о целесообразности закупки, если оборудования нет на складе? Процесс описан так, будто любая закупка одобряется автоматически.
   
# Task 2
# Системный анализ: Функциональность публикации товара на маркетплейсе
## Постановка задачи
Спроектировать логику работы новой функциональности — публикации товара на витрине маркетплейса. Задача включала создание верхнеуровневой User Story, детализацию в формате Use Case и построение диаграммы процесса.

## Формализация требований

### User Story
**Как Продавец**, я хочу отправить оформленную карточку товара на публикацию, **чтобы** товар прошел необходимые проверки и стал доступен для покупки на витрине.

### Сценарии использования (Use Cases)
Спроектирован алгоритм, учитывающий различные маршруты публикации:
1. **Happy Path (Авто-публикация):** Успешная техническая валидация -> Категория не требует премодерации -> Присвоение статуса "Опубликован" -> Индексация в поиске -> Уведомление продавца.
2. **Альтернативный сценарий (Ручная модерация):** Выявление категории высокого риска -> Смена статуса на "На модерации" -> Проверка сотрудником маркетплейса -> Одобрение/Отказ.
3. **Обработка исключений:** Ошибки заполнения обязательных полей (возврат на этап редактирования с подсветкой ошибок).

## Визуализация логики (UML Activity Diagram)
Для наглядной демонстрации алгоритма и точек ветвления разработана Activity-диаграмма. 

**Особенности модели:**
* **Логическое группирование:** Выделены зоны ответственности — базовая системная валидация и бизнес-логика модерации.
* **Ветвления (Decision Nodes):** Четко прописаны условия перехода (наличие ошибок, необходимость ручной проверки, вердикт модератора).
* **Терминальные состояния:** Показаны все возможные исходы процесса (товар опубликован, процесс прерван из-за ошибок, публикация отклонена модератором).
